# Code Modularity Audit

本审查基于当前活跃目录中的 Python 和 SQL 文件，排除了 `.venv/`、缓存、
临时审计脚本和导出产物。目标不是机械地让所有文件一样长，而是让页面只做
编排、业务规则有明确归属、相似模块集中，并将目录稳定在约 4–5 个核心文件。

## 已完成

- `sql/` 根目录的混合脚本已按权限、售后、生产和库存子领域归档。
- 库存 SQL 又按结构、操作、货柜、计划、成本、导入和数据修复区分。
- 应用内所有已发现的 SQL Editor 提示已改为新路径。
- `sql/README.md` 记录目录职责和后续拆分规则。
- 库存多语言静态词典已迁入 `ui/inventory/i18n_catalog.py`，
  `ui/inventory/i18n.py` 只保留 Streamlit 状态与渲染适配，并维持原公开接口。
- Google Sheets 范围匹配与 S2B 可见按钮点击已分别收敛为共享集成助手，
  删除同步和浏览器调用链中的逐字重复实现。
- 物流页面控制器已从千行级缩减为约 55 行，只保留页面入口与标签编排。
  ERP同步放在 `sync_view.py` 和 `source_gateway.py`；物流审核拆到
  `ui/logistics/review/` 的模型、视图、OCR执行、格式化和状态组件。
- 原 600 余行 USPS 查询控制器已拆到 `ui/logistics/tracking/`，分别负责
  输入规范化、查询与缓存、面单信息、始发地展示和页面编排。
- 原 583 行库存历史控制器已拆为 `history/core/` 的批次、筛选、表格和
  数量搜索组件，以及 `history/workflows/` 的撤销、修正和 SKU 历史流程；
  库存变动核对继续复用统一的 `adjustment_preview` 契约。
- 跨账本库存写入的三段式核对已集中到 `ui/operations/stock_review.py`，
  生产库存与耗材库存统一使用 `当前库存 / 本次变动 / 调整后库存` 契约；
  盘点比较与宽表编辑分离，销售、出库、货柜入库、修正和撤销继续组合
  同一契约。
- 生产库存、耗材、销售 Invoice 与仓库调拨的批次撤销 UI 已统一组合
  `ui/batches/actions.py`，数据库分派继续由 `db/batches/lifecycle.py` 负责；
  货柜撤销因包含货柜状态转换而保持独立。
- 货柜表已拆为输入规范化、展示转换和汇总表；出库已拆出包装规格来源与
  持久化校验，避免页面重复查询和签名比较。
- 到货预测已拆为核心计算、货柜时间线和管理/核对视图；UV 与彩色消耗页面
  分别收敛到专属视图，彩色生产同步也分离来源读取和模型计算。
- 衣服、UV 与耗材的库存覆盖、目标库存、建议点货、箱规换算和多批在途缺口
  已收敛到 `db/planning/stock.py` 的无状态计算契约；各领域只保留数据来源、
  消耗窗口、SKU 映射和单位换算适配，不再各自维护点货公式。
- 黑白、彩色、UV 与耗材日耗适配器统一输出 `db/planning/usage.py` 的证据
  契约；删除 UV 消耗模型页独立维护的最近货柜覆盖计算，全部在途联动只由
  库存点货工作流计算，并在完整明细中保留日耗来源。
- 点货风险状态集中到 `db/planning/status.py`；生产库存与耗材页面共用
  `ui/planning/components.py` 的目标天数控件和管理摘要。库存计划同时展示
  原始建议点货量与扣除全部已分配在途后的建议量，耗材混合单位不再错误求和。
- 财务仓储层已拆为库存流水、耗材估值和成本维护；SKU 身份传播与合并预览
  已集中到主数据身份模块。
- 库存仪表盘已拆为总览、批次明细和完成状态，页面控制器只负责编排；
  日耗同步的单来源预览也已抽为独立组件。
- 日常出库已拆为页面编排、SKU 箱规录入、文件导入、库存核对与正式提交；
  继续组合统一的 SKU 排序和三段式库存核对，不再在页面重复实现。
- 货柜 UI 已分离列表、筛选汇总、SKU 明细和包装核对；耗材 SKU 已分离
  新建、目录维护和纯数据模型；客户销售出库已分离客户资料与 Invoice 签发。
- 货柜页面进一步将“在途列表/汇总/明细操作”抽为独立视图，页面入口降为约
  110 行；共享库存筛选器把无状态的数据过滤、标题和选项排序抽为纯模型。
- 手动库存调整与新增 SKU 已拆为独立工作流；财务页面的报表渲染已从页面
  编排中分离。上述控制器均增加自动行数合同，防止后续重新膨胀。

## 已关闭的高优先级队列

原审计中的库存仪表盘、日常出库、日耗同步、货柜表格和耗材库存表格均已完成
职责拆分并通过针对性回归。`ui/inventory/stock/cost_summary.py` 当前是单一成本
汇总视图，虽略高于 200 行，但没有再混入写入流程；后续只有在新增独立业务阶段
时才继续拆分，避免为行数制造无意义转发层。

## 中优先级整理

- `ui/inventory/` 仍保留若干顶层兼容入口，同时已有 `stock/`、`history/`、
  `planning/` 和 `operations/` 子包。确认没有外部调用后，应逐步删除只做转发的
  旧入口，避免新代码继续引用两套路径。
- `db/inventory/` 同时存在顶层模块和 `core/`、`operations/`、`planning/`、
  `master_data/` 子包。顶层文件若仅用于兼容，应标注弃用入口；仍含业务逻辑的
  文件应迁入对应子包。
- `automation/sync/` 混合了日常同步、一次性初始化和历史修复。建议后续分为
  `runtime/`、`imports/`、`maintenance/`，每个目录保留约 4–5 个相关入口。
- `utils/erp/` 按 ERP 平台横向增长。建议每个平台形成包含配置、解析、目录映射
  和规范化的子包，公共协议留在包根部。
- 物流模块后续新增逻辑必须进入现有 `review/` 或 `tracking/` 职责文件，
  `page.py` 不再承载同步、OCR、查询或表格转换实现。

## 审查结论

本轮高风险多职责控制器已经清理完毕。静态词典、平台映射和单一数据算法允许
超过约 200 行；普通页面控制器与新拆出的业务组件由测试合同限制在 200–250 行。
剩余工作属于持续治理：新增页面先查功能目录、组合共享能力，再新增实现；兼容
入口只保留有真实调用者的公开 API。
